# Security model and hardening - CyberDome for NAM

CyberDome reads NAM's eight security tools and, once approved, asks a few of them to act, so it is treated as
production security infrastructure. This document lists the threats, the controls and where each is enforced in
code, the attacks run against the platform and what they found, the build pipeline's controls, and what remains the
responsibility of NAM's hosting environment. Every control named here is checked by a test that runs on every build;
the test is named where it matters.

The platform core (sign-in, access, audit, encryption, the LLM gateway, the action layer) was hardened before the NAM
build, over the earlier rounds summarised in section 3; the NAM modules were attacked in round 39 (section 4).

## 1. Threat model

| Threat | Control | Where |
|---|---|---|
| Stolen / forged API tokens | Entra ID RS256 tokens validated against tenant JWKS (issuer - the tenant's v2.0 or v1 - audience, tenant id, expiry with one minute of skew); an application's own token (no delegated scope) is a service principal, never a person; dev HS256 tokens refused in `prod`, served only to the local machine in dev, and never in front of a real tool (every live connector is isolated while dev sign-in is on); unknown role claims grant nothing; per-token (jti) and per-user (not-before) revocation | `core/auth.py`, `core/access.py`, `connectors/registry.py` |
| Stolen session used for high-impact decisions | Step-up MFA (`amr` = mfa or Conditional Access auth context) required for approvals, rollback, policy, kill switch and access management | `core/auth.py` |
| Insider abuse / over-privilege | RBAC (analyst, lead, admin, automation_admin, auditor) + **domain scoping** (dlp / incident; cross-domain views require all-domain access; out-of-scope records answer 404); **per-role scope**: a principal *sees* the union of its roles' domains but each role *acts* only inside its own (`Principal.acting_in`; a DLP lead who is also an all-domain auditor approves data-protection decisions only); every action decision is judged in the action's domain by `ActionService` itself; policy decisions need an all-domain role; an administrator can grant only scope they manage; separation of duties: no self-approval of four-eyes actions, policies, exceptions or access grants; a privileged platform grant (lead, admin, automation_admin) needs a second administrator and ends within 90 days; rolling an action back is itself an action (policy, four-eyes); turning the kill switch off needs a lead; time-bound, justified platform grants | `core/auth.py`, `core/access.py`, `core/actions.py`, `api/app.py` |
| Compromised integration credential | Service-account API keys: SHA-256 stored, expiry ≤ 365 days, roles limited to analyst / auditor / automation admin, **never** approval, policy or access permissions | `core/access.py` |
| Identity-provider outage | Break-glass: sealed secret, only its hash configured, exchanged once for a 15-minute session token (the secret is accepted on no other route); every use and failure audited and raised as a critical insight; failures throttled per address | `core/access.py` |
| Repudiation of who did what | Append-only access log (ORM refuses update/delete; pruned only by the audited retention job) in addition to the audit chain; **every successful write request is audited** (a generic `api.<method>` event when a route's code wrote none); one trace id links each request or job to every record it caused | `api/app.py`, `core/models.py` |
| Data at rest exposure | Raw payloads, reported emails and **generated reports / evidence packs** encrypted with Fernet (`SOC_DATA_KEY`, rotation with `blobs reencrypt`; mandatory in prod; unsealed data refused in prod); the database on encrypted storage; retention with legal hold | `core/crypto.py`, `core/blobstore.py`, `core/retention.py` |
| Database interception or over-privileged application role | Production refuses a database URL that does not verify the server certificate (`verify-full` / `verify-ca`); the platform runs as a role without schema rights and with SELECT + INSERT only on the audit log; only the migration step holds the owner's credentials | `settings_check.py`, `core/db.py`, deploy manifests |
| Credentials sent to the wrong host | A connector follows a vendor's next link with its credentials only on its own origin (scheme, host, port) | `connectors/http.py` |
| A connector definition file used to run code, write to a tool or exfiltrate | A definition only reads: no actions or look-ups; values pass through a fixed list of converters (no expressions, templates or scripts; parsed with `yaml.safe_load`); paths are relative (`//`, `..`, schemes and hosts refused) and next links to another origin are refused by the transport; credentials are settings, never written in the file; paging is capped per sync; a bad definition is left out and reported | `connectors/declarative.py`, `test_declarative.py` |
| Over-automation (R04) | Autonomy levels L0–L4 per action; destructive actions never autonomous; VIP / critical assets and blast radius force approval; hard blast-radius limit blocks; global kill switch | `core/policy.py` |
| Tampering with evidence / history | Append-only audit table: the ORM refuses UPDATE/DELETE, a database trigger refuses UPDATE / DELETE / TRUNCATE, and the runtime role holds INSERT/SELECT only; SHA-256 hash chain; `/api/v1/audit/verify` and the hourly self-check detect any edit; the chain's head is logged hourly (`audit.anchor`) into the log platform, so even an owner who rewrites every hash cannot match heads already shipped (`audit verify --anchor`) | `core/audit.py`, `core/db.py`, `jobs.py` |
| An action executed but not on record (crash, failover) | `executing` and its audit record committed before the tool call, the outcome after; no lock held during the call; a lost outcome becomes `unverified` with a finding, never a silent re-run | `core/actions.py`, `jobs.py` |
| Duplicate / replayed actions | Idempotency keys, compare-and-set status transitions, pre-conditions re-checked at execution | `core/actions.py` |
| LLM hallucination / prompt injection (R02) | Model sees only retrieved evidence; claims must cite valid evidence ids or are dropped; statements (and summary sentences) stating a figure absent from their cited evidence are dropped (numeric fidelity); time-decayed scores are not given to the model; verdicts, scores and all figures are computed in code; model output can never trigger an action | `llm/gateway.py`, domain services; tested in `test_resilience_security.py` |
| LLM analyst misuse / prompt injection via data | Analyst can only request tools from a fixed read-only catalogue (unknown tools ignored); arguments type-checked; answers must cite tool results; every question and tool call audited | `intelligence/analyst.py` |
| Report builder misuse (prompt-planned reports) | Planner may only choose sources from a fixed catalogue (unknown / case-bound sources dropped); specs validated and size-bounded; figures computed in code, narrative sentences must cite a figure (F#); sections outside the requester's data scope skipped and scope-dependent counts computed for the requester; download requires a scope covering both the report's domains and the builder's scope; case reports require access to the case; compliance data needs the evidence-export permission | `reporting/builder.py`, `api/app.py` |
| Personal-data leakage to the LLM (R10) | Internal users (addresses in the organisation's domains, `DOMAIN\\user` accounts), names, internal host names (under the organisation's domains, and the case's own device names), internal IP addresses, phone numbers, card and national ids pseudonymised before the prompt leaves the platform and restored after - one pseudonym map per call, never shared between parallel calls; prompts/responses logged; approved-endpoint allow-list (mandatory and https-only in prod); model pinning; token budget | `llm/redaction.py`, `llm/gateway.py`, `core/cases.py` |
| Hostile or malformed model output (a field of the wrong type, broken JSON, an absurd report period) | Model JSON is untrusted input: every field is type-checked before use (`model_list` / `model_choice` / `model_ids`), a malformed item is dropped and counted, a planned report period is kept within 1-730 days, and each analyst tool runs in its own savepoint | `llm/gateway.py`, `intelligence/`, `reporting/builder.py` |
| A policy that passes approval but breaks every decision | Autonomy and AI usage policies are validated field by field (types, ranges, known keys) before they can be proposed; a stored entry that cannot be read is decided at L2 (recommend) with four-eyes, never higher | `core/policy.py`, `llm/usage_policy.py` |
| Web attacks on the console | Strict CSP (`script-src 'self'`, no inline script or handlers, `frame-ancestors 'none'`; `connect-src` allows only the origin and `login.microsoftonline.com` for sign-in), all dynamic values HTML-escaped, ids URL-encoded in API paths, deep links restricted to http(s), no-store caching, nosniff, DENY framing, HSTS on HTTPS (also behind a TLS-terminating trusted proxy, via its `X-Forwarded-Proto`) | `api/app.py`, `api/static/` |
| Abuse / DoS | Per-client-address rate limiting (X-Forwarded-For only from configured proxies, and then its right-most hop that is not a proxy; idle buckets evicted, never the whole table), 30 MB request cap enforced on the byte stream (chunked uploads included), 25 MB email cap, **linear-time parsing of hostile e-mail** (every regex over message content is bounded; tested on 2.4 MB pathological bodies), numeric inputs bounded, `/health` anonymous answer minimal and its audit check incremental, no blocking work on the event loop (an upload is processed in the request thread pool), trigram indexes behind the search box, connector request budgets so enrichment cannot degrade source tools (R06) | `api/app.py`, `core/db.py`, `connectors/base.py`, `domains/phishing/agents/`, `llm/redaction.py` |
| Secret exposure | No secrets in the repository; `.env` git-ignored; `<NAME>_FILE` vault mounts supported; per-tool least-privilege service principals, read scopes by default; Microsoft app registrations can use a certificate (signed client assertion) instead of a secret | `config.py`, `config/connectors.yaml` |
| Client data leaving in test fixtures (record-and-sanitise) | Off unless `SOC_RECORD_FIXTURES_DIR` is set; request headers and token / secret / password / key fields never recorded; people, accounts, machines and the client's domains replaced by HMAC-keyed pseudonyms (salt never stored with the recording, so not reversible); internal and public IPs remapped; free text replaced by its length; a scan report of anything still looking like an address or IP; tested to leave no identity of the demo estate | `connectors/recording.py`, `test_recording.py` |
| Secrets leaking through logs | Structured log lines mask values under secret-like keys and cut long values; outbound calls are logged by host and path only (no query string, headers or body); prompts are stored pseudonymised; a caller's `X-Request-ID` is reused only if it is a safe token (no spaces, quotes or control characters - no log injection) | `core/observability.py`, `connectors/http.py` |
| Runaway AI spend (a script, a flood of work, a misbehaving model) | Monthly and daily token budgets, per-person hourly / daily limits, a hard cap on every answer's length, per-feature off switch - set only by administrators (manage_access, MFA), versioned and audited; refused calls are logged with the reason and fall back to deterministic text | `llm/usage_policy.py`, `llm/gateway.py` |
| Tampering with tool configuration (pointing a connector elsewhere, switching a tool off, promoting it to act) | Console changes are proposed by a person with manage_connectors (never an API key or agent) and approved by another with approve_policy and MFA; versioned, audited, re-checked at approval (stale proposals refused, preflight must still match); only pausing - the safe direction - is immediate. Secrets cannot be entered or stored: a secret setting may only be a `${VAR}` reference, the console shows *set / not set* only; export carries no secret values | `core/connector_config.py`, `api/app.py` |
| A broken or malicious connector configuration taking the platform down | Strict schema (unknown tools / keys / stages, malformed values, secrets in clear) refused at start-up and at proposal; a connector that cannot be built is isolated, the rest work; a connector module that fails to import is skipped | `connectors/config_schema.py`, `connectors/registry.py` |
| Irreversible actions run unattended | Password reset, secret rotation and confirm-compromised are marked destructive: whatever the policy says they stop at L3 (a person approves) | connector action factories, `core/policy.py`, `test_irreversible_actions_are_never_autonomous_whatever_the_policy_says` |
| Watch lists used to mislead analysts (an insider exception-listing their own account) or as an upload attack | Changes need manage_watchlists (lead), a person with step-up MFA, never an API key; every upload and removal audited with the values; a match is shown as context only and never changes a severity, verdict or action, and the exception banner says the case is still judged on its evidence. Uploaded workbooks: 5 MB cap, refused if any part declares a DTD or entity or is in a multi-byte encoding (UTF-16 / UTF-32 would hide those declarations from the check) - no XXE / entity expansion; unpacked parts size-capped (zip bombs); cells past column 256 ignored (a cell at Excel's last column would otherwise widen every row to 16,384 cells); 10,000 entries a list; values validated per type | `core/watchlists.py`, `test_watchlists.py` |
| Tuning used to hide real attacks or bend the platform (an insider or a careless lead suppressing a detection, labelling an attack an exercise, marking a containment action as usually rejected; a prompt steering the draft) | Changes need tune_detections in the rule's domain (lead), a person with step-up MFA, never an API key; a **second lead** approves, seeing the preview on past data (including incidents or reports analysts ruled a threat). The model only drafts from a fixed menu, and its values are checked against the request and the data. In code, whatever a rule says: high and critical alerts, deception alerts, exercises and alerts on a host with a KEV-listed vulnerability are never suppressed; 1 in 10 suppressions stays open for QA; a threat found in a suppressed or sampled case pauses the rule; an exercise is still investigated in full; a raise never changes a verdict; a clicked or gateway-flagged report never auto-closes; a KEV-listed finding on an internet-facing asset stays P1 and every KEV finding keeps the P1 SLA; a usually-rejected action is still recommended and shown, only its autonomy is capped, and critical and deception cases are never covered; rules expire (exercises within 30 days, others within a year) and are revocable at once; suppressed incidents are kept and every step is audited | `core/tuning.py`, `test_tuning.py` |
| Hostile report templates or style packs (macros, XXE, zip bombs, image exploits) or a writing guide used to steer the model | Changes need manage_report_style (lead, admin), a person, never an API key; every change versioned and audited. Macro-enabled files and any part with `vbaProject.bin` refused; XML parts declaring a DTD or entity, or in a multi-byte encoding, refused before parsing; 15 MB per file, 60 MB unpacked; logos verified, refused above 5000 pixels a side (a few-byte PNG claiming gigapixels is refused before decoding) and re-encoded as PNG. The writing guide (8,000 characters) enters the prompt as wording rules below the grounding rules: uncited statements and unsupported figures are still removed, and no figure, verdict or action depends on model text | `reporting/style.py`, `test_report_style.py` |
| Investigation values rewriting a vendor query (a host, user or indicator name containing a quote) | Every value taken from investigation data is escaped for the query language it enters: URL path segments percent-encoded (`path_part`), and the query-language escapes of the platform core (`odata_str`, `fql_str`) for any connector that builds a filter - so `o'brien@...` is looked up correctly and a crafted value can neither widen a read nor reach another resource | `connectors/tools/_common.py` (`odata_str`, `fql_str`, `path_part`), `test_tool_onboarding.py` |
| An ownership upload used to misroute work or change priorities | Changes need manage_ownership (lead, admin, automation admin), a person, never an API key; every upload and clear is audited (file, rows, teams); versions kept; it never overrides a CMDB answer; the file goes through the same hardened Excel / CSV reader as watch lists (no DTD / entity / multi-byte encoding, size caps); the export is formula-guarded | `core/ownership.py`, `test_ownership.py` |
| Audit exports opened in a spreadsheet (formula injection) | CSV cells beginning `=`, `+`, `-`, `@`, tab or CR are prefixed with `'`; the .xlsx export writes inline text cells only (never formulas) and strips characters XML forbids; exports need export_evidence with all-domain scope and are themselves audited | `core/audit_export.py`, `test_audit_export.py` |
| Insider text steering a decision (a DLP message body, subject or file name written to talk the AI or an analyst into closing it) | Decisions read structured facts only (`DlpService._facts`: user, data classes, destination class, device state, identity and privileged-access context); the subject and file names are kept apart as `untrusted`, shown to the analyst and passed to the model **fenced, as data**; no rule reads them; no decision lowers a severity on content; the destination is kept only when it is a real host name (anything else is `unknown`, judged as outside) | `domains/dlp/service.py`, `test_dlp.py::test_text_the_sender_wrote_never_changes_an_outcome_a_severity_or_a_fact`, `test_pentest_nam.py::test_text_a_sender_writes_never_becomes_the_destination_fact` |
| The AI closing what it must not (earned autonomy abused or drifting) | The AI may escalate alone but close only when the computed disposition agrees; never closed automatically: high / critical, privileged users, deception hits, hosts with a known-exploited flaw, the block watch list; a decision without a valid citation falls back to the computed path; every AI decision stored with model, prompt version, evidence hash, output and stage; promotion needs a target the SOC lead set, the measured agreement and a **second lead**; demotion on agreement drop or outcome shift (PSI) needs nobody; the *decide* stage is refused in code in this version | `core/decisions.py`, `domains/dlp/service.py`, `test_decisions.py` |
| Containment run by the platform or by one person | Isolate host, disable account, reset password, confirm compromised and rotate a privileged secret are **containment** (`policy.CONTAINMENT`): always four-eyes and never autonomous **whatever a policy document says** - a document that tries is refused at proposal, one stored earlier is overruled by the engine; every four-eyes action is capped below L4 | `core/policy.py`, `test_core_governance.py::test_containment_stays_with_two_people_whatever_a_policy_document_says` |
| Two people deciding the same thing at the same moment (both "approve") | Every approval, rejection and recorded change of a governed document is an exactly-once transition (`core/db.claim`: `UPDATE ... WHERE status IN (...)`); the reportability decision and each recorded submission use a compare-and-swap on a revision; the loser is told it was decided by someone else | `core/db.py`, `reporting/breach.py`, `test_pentest_nam.py::test_racing_approvals_decide_once_and_leave_one_audit_event` |
| The Dome Score bent to look better (weights or penalties changed quietly) | The weights are a versioned document: previewed, proposed with a reason, approved by a **second lead** with all-domain scope and MFA, audited at every step; every surface reads the approved version; the score can be recomputed from the factors it returns | `intelligence/posture_weights.py`, `test_posture_weights.py` |
| A regulatory decision changed after the fact (restarting a deadline) or taken by the platform | Reportability is decided by a lead in person (never a service key, never the model) with a reason; once reportable it stands - deciding again is refused; the decision is a strict true / false; clocks come from the catalogue with their source and stay "to verify" until checked; the AI only drafts, citing the case's structured facts | `reporting/breach.py`, `test_comply_pilot.py`, `test_pentest_nam.py::test_a_regulatory_decision_takes_a_real_true_or_false` |
| A control catalogue used to inject content or claim compliance | The catalogue is versioned data changed by two people; ids from a fixed character set; every text bounded (4,000 characters, titles 300), nesting shallow, numbers finite, at most 500 controls, 400 KB; tests only from the fixed list; the platform shows evidence and gaps and never says "compliant" | `reporting/regimes.py`, `test_pentest_nam.py::test_hostile_documents_and_values_are_refused_before_they_are_stored` |
| A DLP rule change that hides real data loss | The platform never edits a rule in the tool; a change is refused - at proposal and again at approval - if it would have hidden an alert an analyst escalated, personal data in bulk, a high / critical alert or one on the never-automatic list; a second lead approves; an engineer records it as made; it is verified from the tool's configuration snapshot and later alerts | `domains/dlp/tuning.py`, `test_dlp_tuning.py` |
| A manual run and the scheduled job opening duplicate cases | `POST /dlp/run` and `/crosstool/run` hold the job's own lease (`jobs.held`) and answer 409 while the job runs | `jobs.py`, `test_pentest_nam.py::test_a_manual_run_never_runs_beside_the_scheduled_one` |
| Personal data (PAN, Aadhaar, investor records) leaving India through the model | The model runs in NAM's environment or an Indian region, or is off; `Redactor` pseudonymises identities, names, internal hosts and addresses, phone, card and national ids before any prompt; only the approved endpoint is called; raw vendor logs stay in the deployment's region | `llm/redaction.py`, `llm/gateway.py`, CLAUDE.md §0.4 rule 8 |

## 2. NAM-specific security rules (CLAUDE.md §0.4)

| Decision | Decided by | Enforced by |
|---|---|---|
| Which read-only look-ups an investigation runs | the AI, from a fixed menu of seven (no free-form tool calls, no URLs) | `domains/dlp/investigator.py` (names off the menu dropped; every look-up reads what the platform holds, none calls a tool) |
| DLP disposition: close as benign, escalate | the AI, only once its decision type is promoted, and only to close where the computed disposition agrees; until then a person | `core/decisions.py` (decide refused in this version) |
| A Forcepoint rule change | the AI proposes, a second lead approves, an engineer makes it | `domains/dlp/tuning.py` |
| Reversible actions (ticket, session revoke, require MFA) | recommended (L2) by default; L3 / L4 per action type only by an approved policy | `core/policy.py` |
| Containment (isolate, disable, rotate a privileged credential) | people, four-eyes, always | `policy.CONTAINMENT` |
| Reportability under DPDP / CERT-In, breach notification | a person; the AI drafts | `reporting/breach.py` |
| The Dome Score, coverage, severity, every figure | code; the AI explains | `intelligence/posture.py`, `intelligence/ciso.py` |

Guardrails that hold at every stage, each with a test that fails when it is removed: the never-automatic list, close
only on agreement with the computed disposition, insider-written text fenced and never decisional, citation
required, every AI decision recorded, model off -> computed dispositions with identical figures, 1 in 10 AI closures
re-checked by a person (stable hash).

## 3. Attacks run on the platform core (before the NAM build)

The inherited suite (`test_pentest.py`, 24 attack tests, run on every build) and four review rounds attacked the core
the NAM modules run on. What they established, in short:

| Round | Found and fixed |
|---|---|
| Penetration test 1 (2026-09) | Authentication bypass and token forgery, privilege escalation and cross-domain access by id, injection in every query parameter, path traversal, upload abuse, information leakage, CORS, credential guessing, races on approvals - all refused; the hardening list included the request body cap on the byte stream, out-of-scope records answering 404 and rate limiting |
| Penetration test 2 (2026-09-29), white-box | Role scopes merged across roles (a scoped lead with an all-domain auditor role could approve everywhere) - now each role acts only in its own scope; scoped self-approval outside the scope; a scoped administrator granting beyond the scope; other-domain data on shared screens; ReDoS in message parsing (linear time now) |
| Go-live review (2026-10-18) | Dev sign-in in front of live tools (now every live tool is isolated while it is on); `SOC_TRUSTED_PROXIES` CIDRs that never matched; break-glass sessions derivable from the configured hash (now recorded at the audited exchange); the action executing inside the audit lock; image and dependency CVEs (0 fixable high / critical after) |
| Security audit (2026-11-15) | Unbounded free-text fields, `server` header disclosure, dependency advisories - fixed; the audit made every free-text body field bounded |

`test_pentest.py` keeps running on every build in the full scope; `test_consistency.py` sweeps every GET route with
seven roles and fuzzes every write route, so each NAM route is covered by those sweeps too.

## 4. Penetration test of the NAM surface (round 39, 2026-11-19)

**Method.** The NAM routes were listed from the application and each was probed against a live in-process instance
in the NAM scope with step-up MFA on, loaded with the sample estate (inventory, DLP, cross-tool and posture jobs
run first): every role, a lead without MFA, a lead of another domain, a service key, no credentials; hostile values
(NaN / Infinity, booleans for numbers, oversized and deeply nested documents, script and markup in every text field,
ids out of range); three to four people deciding the same thing at the same moment; text a sender writes in a DLP
incident; a manual run beside the scheduled one. Then a browser tour of every CyberDome screen with a stored-XSS
probe in every field a person writes. The probes became `test_pentest_nam.py` (8 tests) and the NAM browser tour.

**Held:** every lead-only decision (weights, catalogue, pilot figures and baseline, reportability, the report draft,
decision-type targets and stages) refused for analysts, auditors, a lead without MFA, a lead of another domain, a
service key and anonymous callers; a service account cannot hold the lead role at all; the weights validator refused
unknown parts, non-finite and boolean values and an all-zero document; DLP rule-change parameters of every wrong
shape; snapshot routes for unknown or traversal tool names; the cross-domain NAM screens answered 403 to
domain-scoped people; the audit pack only to evidence exporters; no stored XSS on any screen (every value escaped,
strict CSP).

**Found and fixed:**

| # | Finding | Severity | Fix | Test |
|---|---|---|---|---|
| 1 | **Racing approvals.** Two leads approving the same Dome Score weights at once were both told "approved" and two approval events were written; three leads deciding one personal-data incident's reportability all succeeded - the decision that "stands" was the last one, and its regulatory clocks restarted. The same read-check-write existed in every approval path (catalogue, DLP rule changes, decision-type promotions, the autonomy policy, tuning rules). | High | One exactly-once helper (`core/db.claim`: conditional `UPDATE ... WHERE status IN (...)`); the reportability decision and each recorded submission compare-and-swap a revision | `test_racing_approvals_decide_once_and_leave_one_audit_event` |
| 2 | **Containment could be made autonomous.** `four_eyes` added a reason but did not cap the level: a policy version setting host isolation to L4 would have isolated hosts with no person involved, and a version could switch four-eyes off. | High | `policy.CONTAINMENT` always four-eyes and capped at L3 in the engine; such documents refused; every four-eyes action capped below L4 | `test_containment_stays_with_two_people_whatever_a_policy_document_says` |
| 3 | **Sender text became a "fact".** Whatever followed `@` in a recipient (or named a URL's host) was kept as the destination domain, so a sender could put any sentence into the numbered facts, the breach-report draft and the model's narration. | Medium | Only a real host name is kept; anything else is an `unknown` destination, judged as outside | `test_text_a_sender_writes_never_becomes_the_destination_fact` |
| 4 | **A manual run beside the scheduled one** could open two cases for one person. | Medium | The routes hold the job's lease; 409 while it runs | `test_a_manual_run_never_runs_beside_the_scheduled_one` |
| 5 | **Loose regulatory input.** `"reportable": "yes"` (or `1`) was read as true. | Low | strict boolean | `test_a_regulatory_decision_takes_a_real_true_or_false` |
| 6 | **Unbounded catalogue documents and outage entries.** A catalogue title of 50,000 characters and ids with quotes and markup were accepted (the ids enter element ids and CSS selectors on the screen); an outage could name any "tool" and be dated 1900. | Low | ids from a fixed character set, texts bounded, nesting limited; outages only for a known tool within 400 days | `test_hostile_documents_and_values_are_refused_before_they_are_stored` |
| 7 | **Accessibility defects found by the NAM tour** (not security, recorded here because the tour runs with the probe): lever and "hot" text below WCAG contrast, links inside text told apart by colour alone, inherited domain tabs on the Cases screen overflowing a phone | - | text colour tokens, underlined in-text links, the scope's domains only | NAM browser tour |

## 5. Supply chain and build pipeline

| Control | How |
|---|---|
| Reproducible dependencies | `requirements/platform.lock` pins every package (direct and transitive) at an exact version. The container images install from `requirements/image.lock` / `image-engine.lock`: resolved on Linux inside the pinned base image, constrained by `platform.lock`, with a SHA-256 for every file, installed with `--require-hashes`. `python scripts/supply_chain.py lock` / `image-lock` regenerate them; `check` fails when the environment drifts or an image lock disagrees or lacks hashes |
| Pinned inputs | Base images by digest (Dockerfile, Compose, CloudNativePG); CI actions by commit SHA; overlays accept an image digest only |
| Signed images | A `v*` tag builds, pushes and signs both images by digest (cosign keyless; the signature names the workflow and commit); `deploy/kubernetes/policy/verify-images.yaml` admits only those signatures |
| Software bill of materials | `python scripts/supply_chain.py sbom` writes a CycloneDX 1.5 document (component, version, package URL, licence, direct / transitive), deterministic, produced by CI for every build |
| Known vulnerabilities | pip-audit over the platform lock and the engine image lock on every change and in CI; both container images (platform, engine) scanned with Trivy in CI (fails on fixable high / critical). Go-live review scan of the platform image: 0 fixable high / critical (Debian 13.7 base and every Python package) |

## 6. Independent penetration test - scope (planned before NAM's data)

The suites above run on every build; an independent test of the deployed platform is planned before it handles NAM's
data. Scope and rules of engagement:

- **In scope:** the console and API (`/api/v1/*`, `/health`, `/metrics`), Entra sign-in and API keys, authorisation
  per role and data scope (`dlp`, `incident`, all-domain), the SIEM push endpoint, report and audit-pack downloads,
  the approval flows (weights, catalogue, reportability, DLP rule changes, decision-type promotion, actions),
  rate limiting and request limits, the container image and the reverse proxy configuration.
- **Accounts:** one test identity per role (analyst, lead, automation administrator, administrator, auditor), a
  DLP-scoped analyst, one API key; connectors in fake mode, so no NAM tool is touched.
- **Out of scope:** NAM's security tools and their APIs; denial-of-service volume tests against shared infrastructure.
- **Exit:** every high / critical finding fixed and retested before go-live; the report is shared with NAM.

## 7. Console sign-in (production)

With `SOC_AUTH_MODE=entra` the console signs users in with the Entra ID authorization-code flow and PKCE (S256
challenge, random `state` checked on return, verifier kept in `sessionStorage` only for the round trip). The access
token is for the platform API only; the API validates it (RS256, tenant JWKS, audience, the tenant's v2.0 or v1
issuer, tenant id, expiry with a minute of skew) and maps app roles to platform roles; a token without a delegated
scope (an application's own) is a service principal. The console keeps the token in `sessionStorage` (this tab only). `GET /api/v1/auth/config` is unauthenticated by design and returns public values only
(tenant id, client id, scope). Dev sign-in answers 404 in entra mode and in prod. Sign-out also ends the Entra
session. Tests: `test_console_single_sign_on_config_is_public_and_only_in_entra_mode`, the pentest's unauthenticated
route sweep.

## 8. Operator responsibilities (cannot be solved in code)

* Set `SOC_ENVIRONMENT=prod`, `SOC_AUTH_MODE=entra`, `SOC_DATA_KEY`, and (optionally) `SOC_BREAKGLASS_SHA256`;
  keep `SOC_DEV_TOKENS_REMOTE` unset. Configure `SOC_TRUSTED_PROXIES` for the reverse proxy (address or subnet).
* Create Entra app roles `SOC.<Role>` / `SOC.<Role>.<Domain>` (Domain = `Dlp` | `Incident`) and require MFA via
  Conditional Access.
* Run behind TLS (reverse proxy / gateway) and restrict network access to the API.
* Give each NAM tool its own service account with **read** scope first (Phase 1-2 run at stage `read` /
  `recommend`); add the write scope of one action at a time when NAM accepts it (Phase 3). The vendors' permission
  names are confirmed per tool against NAM's installed versions (DEPLOYMENT_GUIDE.md section 5).
* Keep the model in NAM's environment or an Indian cloud region (or off), with `SOC_LLM_APPROVED_ENDPOINTS` set and
  `SOC_LLM_REDACT_PII` on; keep raw vendor logs in the deployment's region.
* Run `init-db` with the schema owner and `SOC_DB_RUNTIME_ROLE`, and the platform as that role (the packages do);
  keep the `audit.anchor` log lines in write-once retention; back up and retain per NAM's policy (CERT-In expects
  logs kept for 180 days - Dome Comply checks it per tool, to be confirmed by NAM's compliance team).
* Deploy images by digest and enforce their signatures at admission; encrypt etcd if any Kubernetes Secret is used.
* Store secrets in a vault and mount them as `*_FILE` (including the notification webhooks).
* Give `automation_admin` / `admin` (propose connector changes) and `lead` (approve them) to different people; give
  the two-lead approvals (weights, catalogue, promotions) to at least two people with all-domain scope.
* Record-and-sanitise only with NAM's agreement: unset `SOC_RECORD_FIXTURES_DIR` after the first syncs, review the
  files and `_scan.json` before anything leaves NAM, keep the salt out of the recording.
